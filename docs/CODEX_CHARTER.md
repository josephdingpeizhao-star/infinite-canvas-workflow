## 3. 工程原则（每次改动都适用）
- **先全局后局部**：动手前读权威文档与相关模块源码，弄清现有架构、既有功能与模块依赖；每个改动放进整体架构里评估影响面，不允许只看局部补丁。
- 工程化、规范化、模块化：职责单一、边界清晰、命名与周边一致。分层惯例：提示词文本归 `codex_dev_downstream.py` 构建层，纯元数据归叶子模块，调度归服务层，前端逻辑优先下沉 canvas-bridge。
- 可维护可扩展、避免冗余：不引入不必要的抽象、开关、环境变量、配置项；常量表达语义；不做与当前任务无关的顺手重构——确有价值就单独立项提出。
- **兼容优先于速成**：新功能优先与现有架构融合，不接受临时性方案换速度；若正确做法更贵，把两个方案的代价与风险摆给用户选。
- **主动谏言**：发现需求有更合理的实现方式、潜在架构问题、性能隐患或维护风险，先说明原因和证据、给出替代建议，等拍板再动手；不机械执行需求。

## 4. 每个任务的标准流程
1. **基线核实**：两仓 `git log` / `git status`；未跟踪文件口径＝脚本类恒为 0、其余逐项对应到已知批次（`manifests/`、`reports/` 的活批次产物**一律不碰**）；分组跑全量测试确认基线绿。与文档记载不符时以现场为准并报告。
2. **勘察 + 方案一次汇报**：只读勘察（引用真实文件与行号），给出方案（改哪些文件、为什么、影响面、兼容性、测试计划、风险与回滚），**待用户批准后实施**。微小零风险改动（拼写、注释、纯文档）可直接做并在汇报中列明。
3. 实施到提交：原子提交、英文祈使句、提交信息含行为变化与真实测试证据；不推送远端（用户要求时才推）。
4. **落账**：更新 `docs/CANVAS_PROJECT_STATE.md`（决策日志、终验记录、待办增减），独立 chore 提交。
5. 终报：结论先行 → 证据（真实测试输出、diff 范围）→ 影响面 → 需要用户亲手做的事。
6. **硬停条件**（任一命中立即停下取证汇报，不自行裁决）：与红线或既定决策矛盾；需放宽任何校验；需改既有测试正文；涉钱、涉密、删数据、不可逆；现场与方案假设实质矛盾。

## 5. 验证纪律（你自己就是质检，证据必须硬）
- 单条工具调用约 124 秒超时：全量测试必须**分组**跑（当前全量约 180 秒），统一 `PYTHONUTF8=1`；**禁止以静态计数或推测替代真实运行**；汇报真实 `Ran N tests / OK` 行与分组清单。
- fork 验证：`web/` 目录下 `bun test` + `bunx tsc --noEmit`。
- 新增防线必须**破坏性白盒自证**：临时削弱被守卫的代码 → 对应测试必须变红（红的原因要与守卫语义对应）→ 复原跑绿。破坏性验证与全量回归**串行**；变异前先确认改动真的落地。
- 变异验证跑完同族全部测试模块；断言异常用最具体子类（父类断言＝假覆盖）；构造探针用生产中真实出现的数据形状（经包装层的，不是裸异常）。
- 涉及安全、披露、费用边界的修改，额外做对抗性反向探测（密钥形状、路径、URL、超长、非字符串等）。
- 复原文件禁用 `git checkout --`（autocrlf 且无 .gitattributes，会写坏行尾造成假红），用 `git show <ref>:<path> > <path>`。
