# 画布原生节点卡片规格书（阶段 5A-R）

> 本文件是纯设计规格，不代表后台已经接入。所有状态仍以仓库事实为准，所有写入和执行仍须经过既有白名单与门禁。

## 共用规则

- 视觉语言沿用 Infinite Canvas 浅色主题：画布 `#f4f2ed`、节点面板 `#fbfaf7`、节点填充 `#e7e5df`、边框 `#d6d3ca`、正文 `#292524`。
- 状态同时使用文字、形状和颜色，不只靠颜色：`idle=待办`、`loading=进行中`、`success=已完成`、`error=需处理`。
- 主旅程从左到右；辅助卡只出现在关联卡近旁。技术字段默认折叠。
- 远看只显示卡片名称、状态、完成数量与阻塞摘要；近看才显示字段、按钮、问题说明与时间线。下述缩放阈值是 5B 可用性测试建议，不是已实现合同。
- 卡片右上角显示卡型编号 K01～K09；业务按钮必须引用 `contract_map_delta.md` 中的旧编号或新增本地行为编号。

## K01 新建批次向导卡

**用途与出现时机**：空画布的旅程起点。收集产品编号、七项确认事实和两类图片资料；创建成功后收起为 K02。

| 承载信息 | 数据来源 |
|---|---|
| 产品编号 | 用户输入 → `build_batch_manifest.py --product-id` |
| 商品品类、高度、手持 2+1、清水、动作禁令、D缺失不补拍 | 用户输入 → manifest `user_confirmed_facts` 七字段 |
| 白底图与风格参考图 | 用户选择；未来由 NC-01 安全资料接收合同处理 |
| 同名冲突与字段错误 | 建批预检结果；错误时零写入 |

**状态机**：`draft`（填写中）→ `validating`（只读预检）→ `success`（创建完成并变为 K02）；任一字段或资料失败进入 `error`，保留已填内容并指出具体缺项。

**按钮与合同**：选择白底图 C16/NC-01；选择风格图 C17/NC-01；检查并创建 C18/NC-01。不得出现真实执行或费用按钮。

**尺寸与缩放**：近看建议 `760×730`；中景折叠为两步摘要；远看收为 `320×160`，只显示“新建批次、已填几项、是否可创建”。

## K02 批次总览卡

**用途与出现时机**：批次建立后一直保留，作为整条旅程的空间锚点；关账后转为归档态。

| 承载信息 | 数据来源 |
|---|---|
| 批次编号、当前阶段、下一步 | `state_reader.read_batch_route()` → `product_id`、`current_stage`、`next_required_skill` |
| 缺失项与阻塞 | route → `missing_required_artifacts`、`blocked_reasons` |
| 已有产物与输出数量 | route → `available_artifacts`、`artifacts.*.file_count`、`outputs.*.file_count` |
| 最后更新时间 | route 读取时刻；界面必须标明“同步中/最后更新” |

**状态机**：`idle`（已建批等待开始）→ `loading`（关联阶段执行中）→ `success`（全部完成并归档）或 `error`（存在阻塞；显示可行动说明）。

**按钮与合同**：刷新 C21；查看产物 C22；继续当前批次 C07（修订为聚焦当前阶段）；打开批次列表 C02。

**尺寸与缩放**：标准 `320×260`；远看只显示批次名、`已完成/总阶段`、当前状态和下一步。

## K03 阶段卡

**用途与出现时机**：现有 `wf:` 阶段/门禁节点的友好化形态，建批后按依赖从左到右铺开，始终保留。

| 承载信息 | 数据来源 |
|---|---|
| 阶段名称、依赖与产物 | `workflow_graph.template.json` 当前节点与连接 |
| 待办/当前/完成/失败 | `state_reader` route + projector 现有 `status` 推导 |
| 当前可运行步骤 | `run_controller.runnable_steps()` 的现有结果 |
| 阻塞原因 | route → `blocked_reasons`；展示为人话摘要 |

**状态机**：`idle`（待办）→ `loading`（进行中）→ `success`（完成）；门禁拒绝或执行失败为 `error`。成功阶段不得因后续失败而退回待办。

**按钮与合同**：开始下一步 C23 → `run: next`；具体重试由 C43 → `retry: <step>`；技术详情 C41。

**尺寸与缩放**：近看 `280×220`；中景 `220×160`；远看 `180×110`，保留序号、标题、状态和一项关键数量。

## K04 产出声明卡

**用途与出现时机**：现有 `wfedit:` 配置节点换装。建批后与 K02 相邻出现，保存后折叠为只读摘要。

| 承载信息 | 数据来源 |
|---|---|
| 主图、详情图、最终提示词、QC报告选择 | manifest `requested_outputs` |
| 批次备注 | manifest `notes` |
| 保存后路由影响 | `batch_editor` 改后 manifest 干跑 `route_batch()` 的结果 |

**状态机**：`idle`（摘要）↔ `editing`（展开编辑）→ `validating` → `success`；非法值或路由冲突为 `error` 且不写入。

**按钮与合同**：四项勾选 C24～C27；备注 C28；保存 C29；打开/收起属于 D05 本地行为。

**尺寸与缩放**：展开 `360×420`；折叠 `300×160`；远看只显示“已声明 4 项产出”。

## K05 费用确认卡

**用途与出现时机**：只在可能产生真实费用或需要独立批准的步骤前出现，紧邻关联 K03；确认或取消后消失。

| 承载信息 | 数据来源 |
|---|---|
| 目标步骤与最大处理数量 | `run_controller` 已解析目标 + 执行预检摘要 |
| 资料完整性、输出覆盖风险 | `state_reader` route 与完整性门禁结果 |
| 服务配置状态 | 未来状态接口只返回“已配置/未配置”，不得返回密钥 |
| 预计耗时与费用提示 | GAP-10 建议元数据；只给范围，不承诺精确值 |

**状态机**：`idle`（等待用户确认）→ `loading`（服务端验证一次性确认）→ `success`（转为 K06）或 `error`（确认失效/预检变化，要求重新查看）。取消直接移除卡片，不发送命令。

**按钮与合同**：费用勾选 C31/NC-02；取消 C30；确认并执行 C32。确认不得保存为长期自动开关。

**尺寸与缩放**：近看 `610×650`；远看仍保持醒目的“费用步骤/待确认”，不得折叠到看不见风险。

## K06 运行进度与时间线卡

**用途与出现时机**：现有 `wfrun:` 与 `wflog:` 的友好组合；执行开始后出现，终态后压缩为成功摘要或失败求助摘要。

| 承载信息 | 数据来源 |
|---|---|
| 当前步骤、开始时间、终态 | `<product_id>.events.jsonl` → `step_started/step_succeeded/step_failed` |
| 已完成数量与正式文件 | route → `outputs.renders.file_count/files` |
| 人话时间线 | 事件 `ts`、`event`、`step`、脱敏 `detail` |
| 已有结果是否保留 | 执行器结果摘要；失败时必须明确说明 |

**状态机**：`idle`（等待开始）→ `loading`（进行中）→ `success`；失败为 `error`，绝不自动重试。失败终态可通过 C43 回到同款确认门。

**按钮与合同**：查看时间线 C46；技术详情 C41；返回总览 C03；准备受控重试 C43。

**尺寸与缩放**：进度卡 `540×470`，时间线卡 `500×540`；远看可合并为一张 `320×170` 摘要，保留步骤、进度、耗时和终态。

## K07 图片结果卡

**用途与出现时机**：沿用 Image/输出节点能力，图片生成后逐张出现；QC完成后附加“通过/待复核/不合格”状态，关账后归入 K09。

| 承载信息 | 数据来源 |
|---|---|
| 文件名、数量、尺寸 | route → `outputs.renders.files/file_count`；Image metadata 尺寸 |
| 图片级QC状态 | QC `results[]` 按资产聚合 + `issues[].affected_asset` |
| 问题数量 | QC `issues[]` 按 `affected_asset` 计数 |

**状态机**：`loading`（等待图片）→ `success`（文件存在）；QC后继续细分 `pass/needs_review/fail`，但不覆盖底层 CanvasNodeStatus。文件读取失败为 `error`。

**按钮与合同**：查看生成文件 C47；展开该图问题组 C37。不得提供未经确认的“重新生成”快捷按钮。

**尺寸与缩放**：主图卡建议 `170×190`，详情图 `170×230`；远看按“主图6/6、详情8/8”折叠成两组计数。

## K08 QC问题卡

**用途与出现时机**：QC报告出现问题后，每条 issue 形成一张独立卡，靠近对应 K07 或集中到问题泳道；裁定后保留结果并可折叠。

| 承载信息 | 数据来源 |
|---|---|
| 问题编号、严重程度、说明、关联图片 | QC `issues[].issue_id/severity/description/affected_asset` |
| 返修目标 | QC `repair_targets[]` 对应 issue 的目标信息 |
| 人工裁定 | 未来 NC-03 独立终审记录；不得写回 QC 原报告 |

**状态机**：`idle`（待裁定）→ `success`（人工接受）或 `error`（决定返修）；机器 `fail` 不等于自动返修，仍等待人工选择。

**按钮与合同**：展开问题 C37；逐条裁定 C38/NC-03；技术详情 C41。

**尺寸与缩放**：单条近看 `560×80`；远看按图片或严重程度聚合计数，放大后恢复逐条卡片。

## K09 终审与交付卡

**用途与出现时机**：QC完成后以终审态出现；所有问题有裁定后允许关账，并在原位置转为交付物卡。

| 承载信息 | 数据来源 |
|---|---|
| 图片、检查、问题与裁定数量 | QC `checked_assets/results/issues` + 未来 NC-03 终审记录 |
| 最终图片与QC报告 | route → `outputs.renders`、`artifacts.qc_reports` |
| 保存位置 | manifest 声明的正式输出和QC目录 |
| 关账状态 | 未来 NC-03 独立关账事实；QC原报告保持不变 |

**状态机**：`idle`（等待终审）→ `loading`（保存逐条裁定与关账）→ `success`（交付/归档）；存在未裁定问题或保存失败为 `error`，不得显示已关账。

**按钮与合同**：暂不关账 C40；全部接受并关账 C39/NC-03；打开保存位置 C44；下载全部 C45/NC-04；返回批次列表 C02。

**尺寸与缩放**：终审态 `510×620`；交付态 `650×650`；远看只显示“已关账、14张图片、1份QC报告、无返修”。
