# 后端缺口登记册（阶段 5B 决策输入）

本登记册只描述缺口，不在阶段 5A 实现。优先级按“能否让非技术用户安全走完整个 demo 批次”排序。

## 优先级总览

| 优先级 | 缺口 | 对用户的直接影响 | 5B 验收结果 |
|---|---|---|---|
| P0 | 常驻执行服务与单实例锁 | 避免重复执行、重复扣费和两个窗口争抢同一批次 | 同一批次同一时刻只能有一个执行任务，重复请求得到明确提示 |
| P0 | 审批确认服务端接口 | 费用与真实调用不能只靠页面上的勾选框 | 服务端留下不可混淆的确认记录，费用步骤强制二次确认 |
| P0 | 建批表单化入口 | 当前七项信息只能通过脚本参数进入 | 界面提交可安全创建 demo 批次，非法值和重名均零写入 |
| P0 | 状态刷新与推送 | 约 3 秒缓存会让用户误以为按钮没生效或执行卡住 | 显示最后更新时间、同步中和旧数据状态，不重复提交 |
| P0 | 错误文案人话分级 | 原始技术失败不适合直接给运营人员 | 用户先看可行动解释，管理员可展开脱敏详情 |
| P0 | 密钥托管状态 | 密钥输入框会造成泄漏和错误责任边界 | 界面只显示“已配置/未配置”，绝不输入、显示或存储密钥 |
| P1 | 批次索引读取接口 | 当前批次列表需要扫描仓库事实 | 可稳定列出批次、阶段、更新时间和下一步，不混入演示残留 |
| P1 | 人工 QC 裁定与关账 | 当前终审只能靠人工记录到文档 | 逐条裁定可追溯，关账与 QC 原报告分离保存 |
| P1 | 交付物打包下载 | 当前只能按路径手工打开文件 | 安全打包最终成图和 QC 报告，并核对数量与范围 |
| P2 | 耗时与费用提示元数据 | 页面无法可靠给出预计耗时或费用 | 后台按执行器和步骤返回提示区间，不承诺无法保证的精确数字 |

<a id="gap-01"></a>
## GAP-01：常驻执行服务与单实例锁

- 现状：运行台通过临时 `--serve` 进程工作，日常入口只开只读投影。
- 风险：重复启动或重复点击可能造成并发执行、重复写入和真实费用风险。
- 5B 最小方案：demo 执行器前增加批次级单实例锁；锁中显示当前步骤、启动时间和占用者；异常退出可安全释放。
- 不做：任务队列、多人调度、跨公司权限。

<a id="gap-02"></a>
## GAP-02：审批确认服务端接口

- 现状：现有白名单只有 `run:` / `retry:` 命令，没有独立审批事实。
- 风险：页面勾选框刷新后会丢失，无法证明真实费用是否获得批准。
- 5B 最小方案：预检返回步骤、是否有真实成本、确认级别和一次性确认标识；执行命令必须携带有效确认标识。
- 保护：确认标识不得变成长期自动执行开关，不得写入 manifest 或前端本地存储。

<a id="gap-03"></a>
## GAP-03：建批表单化入口

- 现状：`build_batch_manifest.py` 已严格定义产品编号和七项确认信息，但入口仍是命令行。
- 风险：非技术用户无法独立建批；文件资料的复制、重名和路径范围也缺少界面级保护。
- 5B 最小方案：仅接收现有八个事实输入（产品编号 + 七项确认），白底图与风格参考图只允许写进 demo 工作区；沿用现有校验和“不覆盖已有 manifest”。
- 保护：不改变 manifest 结构、字段名、文件命名规则或真实批次目录。

<a id="gap-04"></a>
## GAP-04：状态刷新与推送体验

- 现状：画布读存在约 3 秒缓存，`state_reader` 目前是本地读取能力，不是浏览器状态服务。
- 风险：用户可能在旧状态下重复提交，或把“同步中”误判为失败。
- 5B 最小方案：先做定时刷新，返回 `current_stage`、下一步、缺失项、阻塞项、产物数量和最后更新时间；执行后进入明确的“等待新状态”阶段。
- 后续：中央后台成熟后再换成推送，不在 5B 先做复杂实时系统。

<a id="gap-05"></a>
## GAP-05：错误文案人话分级

- 现状：事件账本已有脱敏 `detail`，但没有稳定的用户级分类和处理建议。
- 5B 最小方案：至少分为“需要补资料”“当前步骤不允许”“服务暂时不可用”“执行失败需管理员处理”“费用确认缺失”五类。
- 显示规则：第一页只给发生了什么、是否保留已有结果、用户下一步；技术信息放折叠区。

<a id="gap-06"></a>
## GAP-06：密钥托管与状态

- 现状：真实图片密钥只允许从服务端临时环境读取。
- 唯一合法 UI 形态：只显示“图片服务已配置”或“图片服务未配置”。
- 永久禁止：密钥输入框、复制按钮、明文尾号、浏览器存储、manifest 字段、事件日志、错误详情回显。
- 5B 验收：查看页面源码、浏览器存储和 demo 日志，均不存在密钥值或可恢复片段。

<a id="gap-07"></a>
## GAP-07：批次索引读取接口

- 现状：`detect_current_state` 能发现 manifest 并逐批检查，但不是稳定的界面接口。
- 5B 最小方案：只读返回批次编号、显示名、阶段、下一步、阻塞数量和更新时间；演示工作区与真实批次要有清晰标识。

<a id="gap-08"></a>
## GAP-08：人工 QC 裁定与关账

- 现状：机器 QC 报告是审计记录，当前用户终审通过由状态账本文字记录。
- 风险：如果直接改 QC 报告，会破坏原始审计证据；如果只改页面状态，刷新后决策丢失。
- 5B 最小方案：新增独立的人工终审记录，逐条引用 `issue_id`，保存裁定、备注和时间；关账只在所有问题有裁定后放行。
- 保护：QC 原报告只读、不覆盖；“全部接受”也必须生成逐条裁定记录。

<a id="gap-09"></a>
## GAP-09：交付物打包下载

- 现状：可从 manifest 取得成图和 QC 路径，但没有打包边界。
- 5B 最小方案：仅允许打包 manifest 声明的正式成图和唯一 QC 报告；返回文件数、总大小和完整性结果。
- 保护：不包含提示词、源图、密钥、事件账本、审计备份或临时文件。

<a id="gap-10"></a>
## GAP-10：耗时与费用提示元数据

- 现状：事件账本有历史耗时，执行器可判断是否真实调用，但没有稳定的预计费用合同。
- 5B 最小方案：只返回“通常需要几分钟”“可能产生真实费用”“本次最多处理 N 张”等可解释信息；不能把历史单次结果伪装成保证。

## 5B 建议实施顺序

1. 先用 demo 执行器打通 GAP-01、GAP-03、GAP-04、GAP-05。
2. 再补 GAP-02，验证真实成本步骤始终停在二次确认门。
3. 然后补 GAP-08，走完 QC 与关账。
4. 最后补 GAP-07、GAP-09、GAP-10，形成完整但仍然轻量的操作面板。
5. GAP-06 从第一天就是硬约束，不是最后补的功能。
