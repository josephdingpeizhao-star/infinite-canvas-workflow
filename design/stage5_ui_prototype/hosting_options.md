# UI 承载位置对比（阶段 5B 前决策材料）

本页只提供决策材料，本阶段不替用户拍板，也不修改 Infinite Canvas fork。

## 对比

| 维度 | 方案一：在 Infinite Canvas fork 内新增 UI 组件 | 方案二：独立轻量操作面板 |
|---|---|---|
| 用户入口 | 画布与操作界面在同一网页内 | 操作面板负责日常流程，画布保留图形视图 |
| 主要改动 | fork 新组件、页面布局、状态与命令接入；主仓库仍需桥接服务 | 主仓库旁新增独立界面层；通过未来受控服务读取状态和提交白名单动作 |
| fork 纪律 | 必须遵守“新增文件 + 登记锚点”，每次上游同步都要复核 | 不进入 fork，不新增锚点；现有画布投影保持不变 |
| 上游同步成本 | 较高。界面越复杂，与上游页面结构耦合越深 | 较低。Infinite Canvas 升级与操作面板大体解耦 |
| 工作流适配 | 画布上下文天然可见，适合图形定义和节点定位 | 更适合表单、审批、批次列表、QC 和关账等线性任务 |
| 信息密度 | 画布内叠加复杂表单和列表后容易拥挤 | 可针对运营任务使用标准表单、表格和固定导航 |
| 费用门禁 | 需要在画布交互中增加明显确认层，容易与节点命令混在一起 | 可把预检、费用二次确认和执行状态做成完整流程 |
| 维护责任 | 同时维护 fork、桥接层和 UI 组件 | UI 与服务边界清楚；画布继续只维护图形能力 |
| 中央后台衔接 | 将来仍需把 fork 内本地状态迁出 | 更接近公司统一后台的最终形态，可逐步替换本地读写实现 |
| 适合的核心任务 | 定义和观察工作流图 | 新建批次、声明产出、执行确认、QC、终审和交付 |

## 建议

建议阶段 5B 选择 **方案二：独立轻量操作面板**，同时保留 Infinite Canvas 作为工作流图形视图。

理由：

1. 唯一验收剧本是线性的“建批到关账”，标准操作面板比无限画布更适合表单、审批、问题列表和交付物管理。
2. 不进入 fork，可以避免新增锚点和持续上游同步成本，符合当前低侵入纪律。
3. 现有写入合同本来就在主仓库桥接层，独立面板更容易把所有动作统一送入白名单和审批门。
4. 将来迁移到中央后台时，界面结构和用户旅程可以保留，只替换本地服务实现。
5. 画布仍有不可替代的价值：呈现工作流结构、节点依赖和整体状态；它不需要同时承担所有运营表单。

## 方案二的最小形态

- 顶部显示当前是演示环境还是真实环境。
- 批次列表和九屏旅程使用同一套状态语言。
- 所有写入先进入受控服务，再由服务映射到 `requested_outputs`、`notes`、`run:` 或 `retry:`。
- 新合同动作在后台补齐前保持禁用或明确显示“尚未接入”。
- 画布提供“查看工作流图”链接；操作面板不复制画布编辑能力。

## 暂不决定的内容

- 技术框架与新增依赖。
- 部署位置和公司网络入口。
- 用户权限与多人协作。
- 中央存储、任务队列和通知。

这些都超出阶段 5A，也不影响先用静态原型验证用户旅程。
